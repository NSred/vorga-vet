# Test environment on Render and Neon

Status: Implemented; first deploy pending. Runs the same images as
[the Compose setup](../../compose.yml) and deploys after the existing
[build workflow](../../.github/workflows/build.yml) passes. Setup steps are in the
[DevOps runbook](../../devops/README.md).

## What this adds

The clinic can use VorgaVet from a browser at a public `onrender.com` address while the product
is still in development. A merge into `main` that passes CI redeploys it without any manual step.
It costs nothing and needs no payment card: the frontend is a Render static site, the API is a
Render free web service built from its Dockerfile, and the database is a Neon free project in
Frankfurt. It starts with the existing demo seed data.

Out of scope: importing reference data (species, breeds, allergens, diagnoses) from the legacy
app, which gets its own document; verifying the email of a veterinarian account; a custom domain;
paid hosting.

## Configuration contract

The API reads everything from configuration, and on Render every value is an environment
variable on the `vorgavet-api` service. Nothing secret is committed.

| Variable | Value on Render | Why |
|---|---|---|
| `ASPNETCORE_ENVIRONMENT` | `Production` | Swagger, detailed error pages and `appsettings.Development.json` stay off |
| `PORT` | `8080` | The port Render routes to; the image already listens on 8080 |
| `ConnectionStrings__Database` | entered once in the dashboard | Neon direct endpoint, key-value form, `SSL Mode=Require` |
| `Jwt__Secret` | generated by Render | 256 random bits, never seen by anyone; the committed dev secret is not used |
| `Jwt__Issuer`, `Jwt__Audience` | `vorga-vet`, `vorga-vet-test` | Tokens from a local run are not valid here |
| `Jwt__ExpirationInMinutes` | `60` | Same as Development; the base file has `0` |
| `Clinic__VeterinarianEmails__0`, `__1` | entered once in the dashboard | Who gets the vet role at registration and next login |
| `Database__MigrateOnStartup` | `true` | New flag, see Design |
| `Seeding__DemoData` | `true` | Existing flag; the seeder skips rows that already exist |
| `ASPNETCORE_FORWARDEDHEADERS_ENABLED` | `true` | The client IP comes from `X-Forwarded-For`, so rate limits are per user and not shared through Render's proxy |

The static site has two build variables: `VITE_API_BASE_URL=/api` and `NODE_VERSION=24`.
`Cors:AllowedOrigins` stays empty because the browser only ever talks to the static site's origin.

## Design

**Two services on Render, the database on Neon.** Render's own free Postgres is deleted after
30 days, and Neon's free plan does not expire. Neon supports `pg_trgm`, which the migrations
create. The API uses Neon's direct endpoint, not the `-pooler` one, because migrations should not
go through a transaction-mode pooler and a single API instance needs only a few connections. Both
providers run in Frankfurt.

**Same origin through a rewrite.** In Compose, nginx serves the frontend and forwards `/api/` to
the API with the prefix stripped. On Render the static site does the same job with a rewrite rule
from `/api/*` to `https://vorgavet-api.onrender.com/*`, placed before the single-page-app fallback
`/*` to `/index.html`. The frontend build is unchanged (`/api`), there is no CORS, and refresh
tokens stay in `localStorage` as they are now. If the rewrite turns out not to forward a request
type properly, the fallback needs no code: build with the API's full URL and set
`Cors__AllowedOrigins__0` to the static site's address.

**Production, not Development.** Running the API as Development would have been the shortest
route because it already applies migrations, but it publishes Swagger, returns stack traces and
loads the committed development secrets. Migrations therefore move behind a configuration flag,
`Database:MigrateOnStartup`, in the same style as `Seeding:DemoData`. Development turns it on in
`appsettings.Development.json`, so `docker compose up` behaves as before. Swagger stays tied to
Development.

**Logging to the console.** Serilog takes its sinks from configuration, and before this change
only the Development file configured any, so a Production container logged nothing. The base
`appsettings.json` now has a console sink, which Render shows in its log stream. Development keeps
adding Seq on top.

**Two health endpoints.** `health` checks Postgres and stays as it is. A new `health/live` answers
without touching the database, and Render's health check uses it. Render probes the health path
every few seconds while the service runs, and the interval cannot be changed. If that probe
queried Neon, the database would never suspend, and keeping the API awake around the clock would
use about 186 of Neon's 100 free compute hours a month. The optional external pinger that keeps
the API from sleeping also calls `health/live`, every 10 minutes, under Render's 15-minute idle
limit.

**Deploy flow.** The Blueprint lives in `devops/render.yaml`, where `devops/README.md` says
deployment manifests belong; Render reads it from a custom path. Both services deploy from `main`
with `autoDeployTrigger: checksPass`, so a merge deploys only after `build.yml` is green. Each
service has a `rootDir`, so Render redeploys only the one whose folder changed. Migrations run as
the new API container starts, so a schema change ships with the code that needs it.

**Accepted limits of the free tier.** The API sleeps after 15 idle minutes and takes about a
minute to wake. Uploaded images are on the container's disk and disappear on every deploy or
restart. Bandwidth is 5 GB a month and there are no backups beyond Neon's six-hour restore
window. The vet-role gap stays open for now: the vets register their own accounts before the
address is shared, and the client is asked to type only made-up data.

## Notes from implementation

- On this Windows machine, an Application Control policy blocks freshly built `Infrastructure.dll`
  from loading, so architecture and integration tests fail before running. They pass in a Linux
  container: `mcr.microsoft.com/dotnet/sdk:10.0` with the Docker socket mounted and
  `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal`, working on a copy of `backend/` without
  `bin` and `obj`.
- `WebApplicationFactory` runs the integration tests as Development, so they pick up the
  migration flag from `appsettings.Development.json`, but the factory also migrates on its own.
  The tests therefore do not prove the flag; the Production rehearsal did.
- `Serilog` arrays merge by index across configuration files. Console sits at index 0 in both
  files, so Development keeps Console and adds Seq at index 1 without repeating anything.
